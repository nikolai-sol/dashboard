# Abbott — операторские инструменты конвейера направлений

Скрипты собирают decision-файл для батча согласования. Раньше жили в `/tmp` на сервере
и терялись при перезагрузке; здесь — рабочая копия, на сервере постоянная лежит в
`/root/reportingdash-private/abbott/operator-tools/`.

## Что это

| Файл | Назначение |
|---|---|
| `build_decisions_v4.py` | развёрнутые формулировки обоснований |
| `build_decisions_v5.py` | то же, но короткий текст reject — нужен при больших батчах |

Обе версии одинаковы по логике. Разница только в тексте `REJECT`, и она принципиальна:
приёмка читает decision-файл с потолком **8 МБ** (`local_acceptance.py`, `_MAX_BYTES`).
При 14 тысячах reject-решений развёрнутая формулировка даёт 11.5 МБ и файл отвергается
как `LOCAL_DECISION_FILE_INVALID`. Версия v5 укладывается в 6.7 МБ.

## Запуск

```bash
python3 build_decisions_v5.py <batch_id> <путь_к_decision_файлу> <predecessor_release_id>
```

Скрипт читает `/tmp/reject_paths.json` — список путей, которым назначается
`url_alias_decision = "reject"`. Собрать его для батча:

```sql
SELECT url FROM portal_content_approval_items
WHERE approval_batch_id = ?
  AND JSON_UNQUOTE(JSON_EXTRACT(proposal_evidence, '$.registry1.source_name')) = 'observed_page';
```

Пути нормализуются отбрасыванием схемы, query и хвостового слеша.

Скрипт печатает сводку: `decisions`, `corrections`, `rejects`, `paths_not_covered`, `missing`.
Непокрытые пути — это адреса, у которых уже есть сущность каталога; reject к ним неприменим,
и это нормально.

## Зачем нужны reject-решения

Не для «пометки мусора». Гейт кандидата требует `non_content_unresolved == 0`, а этот
счётчик считает строки фактов, у которых нет ни строки каталога, ни записи-исключения:

```sql
selected.source_row_fingerprint IS NULL AND exclusion.id IS NULL
```

Принятое reject-решение создаёт исключение и закрывает счётчик. Без него валидация
падает с `CANDIDATE_GATE_FAILED`, даже когда все остальные двенадцать проверок зелёные.

## Ограничение, на которое напоролись 21 августа

При 14 144 reject-решениях материализация падает с `SOURCE_PROVENANCE_COLLISION`:
проверка требует уникальности пары `(source_sheet, source_row_ordinal)` среди строк
каталога, а reject-события тоже порождают строки под листом `local_observed_page`.
Их номера сталкиваются с уже унаследованными.

Массовая отбраковка — не выход. Корень в том, что портал плодит уникальный адрес на
каждый экземпляр мероприятия: 13 689 путей `/events/*` при 15 732 просмотрах, из них
13 609 с нулём или единицей просмотров. Встречаются и явные артефакты, например
`/events/vypolnyayetsya-polucheniye-dannykh-podozhdite-neskolko-sekund-a-zatem-` —
текст состояния загрузки, ставший адресом.

Правильное решение — нормализовать `/events/<слаг>` → `/events/` там, где формируются
факты. Эффект посчитан: путей станет 1193 вместо 14 880, просмотры сохранятся полностью
(345 443), детализация потеряется у восьми мероприятий с трафиком не выше 30.

Править таблицу фактов руками нельзя: `scope_hash` считает канонический писатель, и
формула сборщика (`sha256("pages|counter|day|url|title")`) для релизных фактов
не воспроизводится — проверено на пяти строках, не совпало ни одной.
