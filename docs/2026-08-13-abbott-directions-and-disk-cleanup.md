## 1. Исходная проблема

В дашборде Abbott у множества очевидных материалов пустовала графа «Направление».
Пример от заказчика: `/academy/articles/alternativnaya-terapiya-klimaktericheskogo-...`

Разбор показал **две независимые причины**, которые до этого смешивали в одну:

| Вкладка | Откуда берётся «Направление» | Лечится |
|---|---|---|
| 2. Действия пользователя | направление **пользователя** из `portal_user_directions_private` | только свежей выгрузкой из Bitrix |
| 3. Статистика страниц / 3.1 / Возвраты | направление **страницы** из `portal_content_catalog` | канонической классификацией |

Работа по классификации материалов на вкладку 2 не влияет вообще. Справочник
пользователей оборван на `USER_ID 81311`: за июль 1102 активных пользователя,
направление есть у 104 (9.4%); визитов с направлением 136 из 12 218 (1.1%).

## 3. Логика разметки служебных страниц

**12 маршрутов внесены в реестр**, а не выданы исключениями. Причина: исключение
привязано к конкретному батчу (`exclusion.approval_batch_id = candidate_batch.id`)
и требует переиздания в каждом релизе — так у предыдущего оператора накопилось
2980 событий. Запись в реестре живёт постоянно и даёт странице настоящий ярлык.

**58 URL — отревьюенные исключения** (`reject`): наблюдаются в аналитике, но
отсутствуют в утверждённом реестре. Придумывать им направление означало бы
выдумывать данные. Решение обратимо.

**2 PDF** `/local/build/docs/articles/*.pdf` сознательно отнесены к исключениям,
а не к служебным: это файлы статей, а не страницы портала.

## 4. Хабы с фильтрами — правка приложения

Ревизия `e89f760`, ветка `codex/abbott-hub-direction-from-filter`.

`/preparation/` — каталог препаратов: 822 варианта адреса, 7430 просмотров за июль
(74% всего «Не определено»). Дашборд отбрасывает query, поэтому все варианты
схлопывались в одну строку без направления.

| направлений в фильтре | просмотров |
|---|---|
| 0 (весь каталог) | 2387 |
| **1 (однозначно)** | **948** |
| 2 и более | 4095 |

Направление берётся из `direction[]` **только** при ровно одном известном разделе
и **только** когда каталог сам не имеет решения. Несколько направлений, пустой
фильтр, неизвестный ID, страница с определённым направлением — значение каталога
не трогается. Соответствие «ID → направление» выводится из меток каталога, не
захардкожено, поэтому не разъедется с таксономией.

Тесты: 596 passed, из них 5 новых на все граничные случаи.

## 5. Чистка диска

Деплой упал на `npm ci` с `ENOSPC`: свободно было 130 МБ при потребности ~1 ГБ.
Место держали 7 старых worktree, у каждого свой `node_modules`.

Перед удалением каждый worktree проверялся заново: **0 несохранённых файлов,
0 неотправленных коммитов**. Удалялись только `node_modules` — артефакт сборки,
восстанавливается через `npm ci`, исходники и история не затрагиваются.

```
abbott-material-metadata-fix, abbott-return-page-url-projection,
abbott-telegram-completion-label, abbott-user-actions-aggregation,
gidrofuril-direct-transform, gidrofuril-manual-bindings
```

Освобождено 4613 МБ (130 → 4743 МБ). Worktree `abbott-hub-direction` не тронут —
его `node_modules` нужен для выкладки.

Чтобы вернуть любой из них в работу: `cd .worktrees/<имя> && npm ci`.

## Почему «архив» не применили

Клиент пометил 25 страниц снятыми с публикации. Проверка по сети: **ни одной 404**, все
отдают 200, а 22 из 25 собрали 129 просмотров с 1 июля. Пайплайн требует доказательства:

```python
direct_archive_evidence = explicit_archive_override or http_status in {404, 410}
```

Заявлять `explicit_archive_override` не стали — это подпись под фактом, опровергнутым
проверкой. Семи страницам, где направление однозначно следует из адреса (бронхит,
тонзиллофарингит, инфекции ВДП, аденоидит → респираторное; фенофибрат, омега-3 →
кардио; НАЖБП → гастро), направление проставили без архивации. Восемнадцать остались
«Не определено»: у `/tables/NNNNNN` и брошюр по номеру признаков направления нет вовсе.

## Справочник МНН

Присланный «Реестр МНН» оказался тем же `registry1` с заполненной колонкой «МНН» —
2626 значений, идентичных тем, что уже лежали на сервере. МНН материализуются в
отдельную таблицу `portal_content_catalog_mnn`: 1048 связок на 816 материалов.

Снимок `102` от 19 августа содержал 167 отклонённых значений-заглушек и блокировал
контентный гейт, который требует нулевых отклонений у всех снимков кандидата.
Почистили источник, переимпортировали — снимок `116`, отклонений 0, связок те же 1048.

Порядок операций: откат 39 → 38, бэкап БД 847 МБ, `abbott_mnn_successor` поверх 38 со
снимком 116 → релиз 42, валидация, активация. МНН отсутствовали в дашборде около
десяти минут.

## Где остановились

Контентный кандидат собирается и несёт правки — в релизе 43 «Не определено» падает
с 236 до 96. Но валидация не проходит: `non_content_unresolved = 12 140`. Закрыть их
reject-решениями не удаётся, материализация падает с `SOURCE_PROVENANCE_COLLISION`.

Причина не в конвейере: 13 615 из 14 161 адресов — `/events/…` с уникальным номером
на экземпляр. Нужна нормализация на стороне формирования фактов. Расчёт эффекта и
ограничения — в `ops/abbott/README.md`.

**Состояние:** активен релиз 42, дашборд работает, МНН на месте, правки не потеряны.
