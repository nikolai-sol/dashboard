# Защита общего релиза дашбордов

## Решение

Текущий `dashboard-next` остаётся одним приложением для Zaruku, Abbott и
рекламных дашбордов. Один деплой поэтому по-прежнему заменяет весь runtime, но
перед активацией кандидат обязан доказать, что он содержит как актуальный
`origin/main`, так и commit текущего production-релиза.

Разработка каждого типа продолжается в отдельной ветке и worktree. Ветка типа
дашборда не выкладывается напрямую: перед релизом она объединяется с актуальным
main/production, проходит общие контрактные тесты и только затем активируется.

## Два независимых барьера

1. Проверка происхождения отклоняет dirty worktree и commit, который не содержит
   свежий `origin/main` или commit активного production-релиза. Новый релиз
   сохраняет полный SHA в собственном служебном файле. Для первого перехода
   допускается безопасное чтение SHA из имени старого релиза.
2. Серверный lock допускает только одну активацию `dashboard-next`. После
   получения lock проверка production-предка выполняется повторно, поэтому
   кандидат, собранный параллельно со свежим релизом, будет остановлен.

## Проверки

Перед upload выполняются полный рекурсивный тестовый набор, typecheck, lint,
public-asset check и production build. Тесты шлюза воспроизводят актуальную,
устаревшую, dirty и параллельную ветки. После активации проверяются release SHA,
health, отсутствие приватных файлов и ключевые контракты Zaruku/Abbott/рекламных
дашбордов.

## Границы

Шлюз предотвращает потерю уже закоммиченного кода, но не превращает типы
дашбордов в отдельные приложения. Решение о выносе Zaruku и Abbott принимается
отдельно после стабильного текущего релиза. CooperVision Sales Numbers уже
изолирован сильнее: это отдельный runtime, Compose-проект, базы и маршрут.
